# 설계 노트

만들면서 갈렸던 판단들을 모아 둡니다. 코드 주석에도 같은 이야기가 있지만,
파일을 열지 않고도 "왜 이렇게 되어 있나" 를 읽을 수 있게 한 곳에 정리했습니다.

README 가 **무엇을 만들었나**라면, 이 문서는 **왜 그렇게 만들었나**입니다.

---

## 1. 히어로에 어떤 도시가 뜨는가

앱을 켜면 큰 화면(히어로)에 도시 하나가 뜹니다. 그 하나를 이 순서로 정합니다.

```
1) 현재 위치에서 가장 가까운, 목록에 담긴 도시
2) 즐겨찾기 맨 앞
3) 서울 (city_01)
```

**위치가 즐겨찾기보다 먼저인 이유** — 날씨 앱은 "지금 여기" 부터 보여 주는 것이
사람들이 아는 방식입니다. 즐겨찾기한 도시는 어차피 목록 맨 앞에 있어서 한 번만
누르면 되므로, 기본값을 위치로 줘도 잃는 것이 없습니다.

한때 반대로 두었습니다(즐겨찾기 우선). "사용자가 명시적으로 정한 것이 상황보다
우선" 이라는 논리였는데, 관습을 이기지 못했습니다.

**위치는 뒤늦게 도착합니다.** 좌표를 받는 데 몇 초 걸리므로 화면은 먼저 2번으로
그려지고, 좌표가 오면 갈아끼웁니다. 그래서 세 가지 안전장치가 있습니다.

| 상황 | 처리 |
| --- | --- |
| 그 사이 사용자가 카드를 눌렀음 | 위치를 무시합니다. 화면이 저 혼자 움직이면 안 됩니다 |
| 오차 반경이 25km 초과 | 무시합니다 (아래 2번) |
| 권한 거부 · 시간 초과 | 조용히 넘어갑니다. 사용자가 요청한 적 없는 동작이라 실패를 알리면 영문 모를 안내가 됩니다 |

## 2. 위치 정확도를 왜 검사하는가

브라우저가 주는 `coords.accuracy` 는 "이 좌표가 반경 몇 m 안에 있다" 는 뜻입니다.

| 값 | 무엇으로 잡았나 |
| --- | --- |
| 5 ~ 50m | 휴대폰 GPS |
| 30 ~ 3,000m | 노트북 WiFi |
| 10,000m 이상 | **IP 기반 추정** — ISP 허브 위치가 잡힙니다 |

실제로 판교에서 열었는데 대전이 잡히는 일이 있었습니다. WiFi 매칭에 실패해 IP 로
떨어진 경우입니다. 우리 도시들은 서로 50km 안팎으로 떨어져 있어서, 반경 25km 를
넘는 좌표로는 어느 도시가 가까운지 판단할 수 없습니다. 그런 값은 없는 것으로 칩니다.

`maximumAge: 0` 을 준 것도 같은 이유입니다 — 아까 다른 곳에서 잡힌 좌표가 캐시에
남아 있으면 움직여도 그대로입니다.

## 3. 즐겨찾기 순서가 곧 목록 순서

별을 누른 순서가 목록 순서입니다. **최근에 담은 것이 맨 앞**이고, 다시 담으면
(껐다 켜면) 그 도시가 맨 앞으로 옵니다. 카카오톡 즐겨찾기와 같은 감각입니다.

정렬은 세 단계입니다.

```
1) 방금 담은 도시     ← 새로고침하면 사라지는 세션 한정 표시
2) 즐겨찾기           ← 최근 담은 순
3) 사용자가 고른 정렬  ← 이름순 / 기온 높은순
```

**한때 `pinStore` 가 있었습니다.** 대표 도시를 지정하는 핀을 카드마다 달았는데,
즐겨찾기 순서가 같은 일을 더 잘하게 되자 존재 이유가 사라져 걷어냈습니다.
카드에 아이콘이 둘(별 · 핀) 있을 이유가 없어졌고, "핀이 위냐 즐겨찾기가 위냐" 라는
정렬 예외도 함께 사라졌습니다.

기준은 만들 때만 쓰는 것이 아니라 지울 때도 씁니다.

## 4. 지역 검색은 어떻게 동작하는가

이 앱은 처음부터 도시 이름이 아니라 **좌표로** 날씨를 부릅니다. 그래서 사용자가
"속초" 라고 적으면 먼저 그 이름을 좌표로 바꿔야 합니다.

```
"속초" 입력
  → 담긴 목록에서 먼저 찾음                     (통신 없음)
  → 없으면 0.5초 뒤 OpenWeatherMap Geocoding
       1) "속초,KR"    나라를 못 박아 동명의 해외 도시를 걸러냄
       2) "속초"       나라를 풀어 해외 지명도 찾음 ('파리' · '방콕')
       3) "Sokcho,KR"  보정표로 우회 (아래)
  → 후보를 검색창 아래에 표시 → 누르면 담김
```

**버튼을 없앤 이유** — 처음에는 "찾아 담기" 버튼을 한 번 더 누르게 했습니다.
그런데 사용자가 '속초' 를 친 순간 "속초를 찾겠다" 는 의도는 이미 끝났습니다.
거기서 또 묻는 것은 앱의 사정(로컬에 없어서 통신해야 함)을 사용자에게 떠넘기는
일입니다. 호출을 아끼는 문제는 조건(담긴 목록에 없을 때만 · 두 글자 이상 ·
0.5초 디바운스)으로 대신했습니다.

담는 것은 여전히 눌러야 합니다. **후보가 저절로 뜨는 것과 저절로 담기는 것은
다릅니다.**

### 한글 보정표

전국 시·군 135곳을 실제로 돌려 확인했습니다.

| | 결과 |
| --- | --- |
| 한글로 바로 찾음 | 116곳 (86%) |
| 영문으로는 찾음 | 17곳 → `data/placeAliases.js` |
| 둘 다 안 됨 | 2곳 (완주 · 고령) → 군청 소재지 이름으로 우회 |

그래서 우리가 들고 있는 것은 "전국 명부" 가 아니라 **"한글로 안 걸리는 것들"**
스무 줄입니다. 나머지 116곳은 표 없이도 찾아집니다.

**⚠️ 값을 추가할 때는 좌표를 반드시 확인하세요.** 영문 이름이 엉뚱한 곳을
가리키는 경우가 실제로 있었습니다.

```
구례 → 'Gurye'    경기도의 '구례리' (200km 떨어진 다른 마을)
칠곡 → 'Chilgok'  경기도의 '칠곡리' (180km)
```

둘 다 군청 소재지 읍 이름(`Gurye-eup` · `Waegwan`)으로 바꿔 담았습니다.
표에 있는 값은 전부 응답 좌표를 행정중심과 대조해 15km 안쪽인 것만 남긴 것입니다.

### "경상남도 거제시 부근" 은 어디서 오나

OpenWeatherMap 은 한국 주소의 시·도(`state`)를 돌려주지 않습니다. 그래서 응답만으로는
"경남 거제시 옥포동" 같은 문구를 만들 수 없습니다.

대신 우리가 이미 가진 것을 씁니다 — 기본 20곳의 좌표와 행정구역명입니다. 가장 가까운
곳을 찾아 "거제 부근" 이라고 적으면, 어디쯤인지 감이 오고 **같은 이름이 둘 나올 때
구분이 됩니다.**

```
서면 · 경상북도 포항시 북구 부근
서면 · 강원특별자치도 춘천시 부근
```

## 5. 담은 도시의 id 를 좌표로 만든 이유

```
city_01 ~ city_20     기본 명부 (data/cities.js)
geo_38207_128591      검색으로 담은 곳 ← 좌표 × 1000
```

순번(`city_21`)으로 하지 않은 이유 — 지웠다 다시 담으면 번호가 어긋나고, 주소창의
`/weather/city_21` 이 어제와 다른 도시를 가리키게 됩니다. 좌표는 그 지점 자체라
언제 어디서 담아도 같은 id 가 나옵니다. 같은 곳을 두 번 담는 일도 자연스럽게 막힙니다.

## 6. 어떤 값을 store 에 두었나

두 질문 중 하나라도 '예' 여야 store 로 갑니다. 둘 다 아니면 그냥 `ref` 입니다.

1. **화면보다 오래 살아야 하는가?**
2. **트리로 이어지지 않는 두 곳 이상이 쓰는가?**

| 값 | 자리 | 근거 |
| --- | --- | --- |
| ℃ / ℉ 단위 | `configStore` | 앱 바 · 히어로 · 카드 · 상세가 씁니다. 앱 바와 카드는 조상-후손이 아닙니다 |
| 즐겨찾기 목록 | `favoriteStore` | localStorage 와 짝입니다. 저장 watch 가 화면에 있으면 그 화면이 떠 있을 때만 저장됩니다 |
| 담은 도시 목록 | `cityStore` | 목록 화면이 그리고, 상세 화면이 "그런 도시가 있는가" 를 판단합니다 |
| 음악 재생 상태 | `radioStore` | 소리를 내는 `RadioEngine`(앱 셸)과 누르는 `WeatherRadio`(히어로 안)는 형제라 props 로 이을 수 없습니다 |
| 다크 / 라이트 | `App.vue` 의 `ref` | 읽는 곳이 `:class` 한 줄뿐. 자식들은 CSS 변수를 상속으로 받아 테마를 알 필요조차 없습니다 |
| 검색어 · 정렬 · 선택 도시 | `WeatherHomeView` 의 `ref` | 화면을 떠나면 사라지는 것이 맞습니다 |

**store 가 넷이지만 파일 개수는 비용이 아닙니다.** 비용은 전역이 된 *값*의 개수입니다 —
전역 값은 어디서든 바꿀 수 있어서 "왜 이렇게 됐지" 를 추적할 범위가 앱 전체로 넓어집니다.
그래서 하나의 큰 store 에 몰아넣는 쪽이 오히려 나쁩니다. 음악을 고치려고 단위 로직이 든
파일을 열게 되니까요.

## 7. 음악은 왜 화면 밖에 있는가

재생기(`RadioEngine`)는 `RouterView` **바깥**, 앱 셸에 있습니다. 히어로 안에 두면
도시 상세로 넘어가는 순간 unmount 되면서 음악이 끊깁니다. RouterView 가 갈아끼우는
것은 화면이지 소리가 아니어야 합니다.

조작 줄(`WeatherRadio`)은 히어로 안에 있고, 둘은 `radioStore` 를 통해서만 이야기합니다.

### 자동재생이 막히는 것은 정상입니다

크롬은 사용자가 그 페이지를 한 번도 클릭하지 않았으면 소리를 못 내게 합니다.
그래서 재생 상태를 둘로 나눴습니다.

```
intent     우리가 원하는 것   → RadioEngine 이 따라감
isPlaying  지금 실제 상태     → 화면(▶/❚❚)이 따라감
```

하나로 두었을 때는 자동재생이 막히면 버튼이 거짓말을 했습니다 — 소리는 안 나는데
화면에는 ❚❚(재생 중)가 떠서, 한 번 누르면 "정지" 가 되고 두 번 눌러야 소리가 났습니다.

**참고** — 크롬의 자동재생 허용치는 origin 단위로 쌓입니다. `localhost:3000` 과
`localhost:3001` 은 포트가 달라 완전히 다른 사이트로 취급되므로, 포트가 바뀌면
어제까지 되던 자동재생이 안 됩니다. `chrome://media-engagement/` 에서 확인할 수 있습니다.

## 8. 화면을 늘리지 않은 이유

라우트는 넷입니다 — 대시보드 · 소개 · 도시 상세 · 404.

플레이리스트 갈래를 직접 고르는 `/radio` 화면을 만들까 했지만 두지 않았습니다.
**필요해서가 아니라 "메뉴를 추가했다" 고 적기 위해 만드는 화면**이 되기 때문입니다.
날씨가 갈래를 정하는 것이 이 기능의 컨셉이기도 하고요.

대신 확장은 기능과 API 로 했습니다.

| 추가한 API | 쓰는 곳 |
| --- | --- |
| YouTube IFrame Player | 날씨별 플레이리스트 재생 |
| OWM Geocoding `/geo/1.0/direct` | 지역 이름 → 좌표 |
| OWM Reverse Geocoding `/geo/1.0/reverse` | GPS 좌표 → 지명 |
| 브라우저 Geolocation | 현재 위치 |

## 9. 좁은 화면에서 카드를 접는 이유

860px 이하에서는 카드 영역의 자체 스크롤을 풉니다 — 페이지 안에 또 스크롤이 있으면
손가락이 어느 쪽을 미는지 모호해지기 때문입니다. 대신 20장이 통째로 세로로 쌓여서
예보를 보려면 한참 내려야 했습니다.

그래서 처음에는 여섯 장만 보여 주고 나머지는 버튼으로 펼칩니다. 즐겨찾기가 맨 앞에
오므로 자주 보는 도시는 접힌 채로도 보입니다.

접기는 `v-if` 가 아니라 `display: none` 입니다. 펼칠 때마다 카드 14개를 새로 만들지
않아 즉시 열립니다.

**화면 폭 판단은 CSS 한 곳에만 둡니다.** JS 로 `matchMedia` 를 또 재면 창 크기를
바꿀 때 둘을 맞춰 줘야 하고, 어긋나면 버튼만 남거나 카드만 접힙니다.

## 10. 카드 두 줄 높이를 실측하는 이유

넓은 화면에서 카드 영역은 딱 두 줄만 보여 주고 나머지는 스크롤합니다. 그 높이를
`--wx-card-row` 라는 숫자로 손으로 적어 두었는데(294px), 카드 한 장의 실제 높이는
그때그때 달라집니다 — 도시 이름이나 상태 문구가 길어 한 줄 더 접히면(예: '구름 한가득',
'도쿄 하네다국제공항') 카드가 몇 px 자랍니다. 그러면 둘째 줄이 아래에서 잘립니다.

그래서 숫자를 짐작하지 않고 `ResizeObserver` 로 첫 카드에게 직접 물어봅니다.
글자 크기나 여백을 건드려도, 폰트가 늦게 로드돼도 알아서 맞습니다.
